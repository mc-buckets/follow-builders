*Anthropic Engineering: <https://www.anthropic.com/engineering/how-we-contain-claude|How we contain Claude across products>*

A detailed engineering post on how Anthropic limits the blast radius of Claude agents across three products — claude.ai, Claude Code, and Claude Cowork — using three distinct isolation patterns.

_claude.ai_ uses ephemeral gVisor containers (server-side, no local code, per-session filesystem). _Claude Code_ uses an OS-level sandbox (Seatbelt on macOS, bubblewrap on Linux) that cut permission prompts by 84%, paired with an auto-mode classifier. _Claude Cowork_ runs in a full local VM so non-technical knowledge workers don't have to evaluate bash commands.

Key incidents: (1) A pre-trust-dialog hook execution bug — project settings were parsed before users accepted the trust prompt, allowing attacker-authored hooks to run on clone. Fixed by deferring config parsing. (2) A phishing test where an employee was tricked into running Claude with a prompt that exfiltrated `~/.aws/credentials` to an external endpoint — 24 of 25 attempts succeeded; model-layer defenses couldn't catch it because the user was the injection vector. (3) Claude Cowork exfiltration via approved domain — a malicious file embedded an attacker API key and instructed Claude to POST files to `api.anthropic.com`, which the egress allowlist allowed. Fixed with a defensive MITM proxy inside the VM.

The post is essential reading for anyone building agentic products. The consistent lesson: "the software you build yourself is often the weakest."


*Anthropic Engineering: <https://www.anthropic.com/engineering/april-23-postmortem|An update on recent Claude Code quality reports>*

A postmortem on three separate changes that caused degradation in Claude Code between March and April 2026 (all resolved as of April 20, v2.1.116; usage limits reset for all subscribers).

1. _Default reasoning effort change (March 4):_ Anthropic lowered the default from high to medium to reduce tail latency — users objected, saying they'd prefer higher intelligence. Reverted April 7. All users now default to xhigh effort for Opus 4.7, high for other models.

2. _Caching optimization bug (March 26):_ A bug in session-idle context pruning caused thinking history to be dropped on every turn, not just once. Claude became forgetful and burned usage limits faster. Fixed April 10. A back-test using Opus 4.7 found the bug; Opus 4.6 did not.

3. _System prompt verbosity limit (April 16):_ A line added to reduce verbose output — "keep text between tool calls to ≤25 words, final responses to ≤100 words" — caused a 3% drop in coding evaluations. Reverted April 20.

Going forward: broader internal dogfooding of public builds, tighter system prompt controls, broader per-model evals before any prompt change, and gradual rollouts.


*Anthropic Engineering: <https://www.anthropic.com/engineering/managed-agents|Scaling Managed Agents: Decoupling the brain from the hands>*

Introducing Managed Agents, a hosted service in the Claude Platform for running long-horizon agents via stable interfaces designed to outlast any particular implementation.

The core architecture insight: earlier designs coupled the brain (Claude + harness), hands (sandboxes/tools), and session (event log) into one container — making it a "pet" that had to be nursed back to health on failure. The new design decouples all three.

- The harness now calls sandboxes like any other tool: `execute(name, input) → string`. Dead containers don't kill the session.
- The session log is durable and external — a new harness can `wake(sessionId)` and resume from the last event.
- Credentials never enter the sandbox where Claude's generated code runs; git tokens are baked in at clone time, OAuth tokens live in a vault reached via proxy.
- Context management is separated: `getEvents()` lets the harness fetch positional slices of the session log rather than making irreversible compaction decisions.

Results: p50 TTFT dropped ~60%, p95 TTFT dropped over 90%. Containers are now only provisioned if needed (not up front for every session). Multiple brains can connect to multiple hands.
